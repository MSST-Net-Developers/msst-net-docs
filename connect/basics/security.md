## 总览

MSST-Net 的基本原则是：**数据的保密性与完整性只依赖通信双方的密钥**，而不依赖网络中的任何服务器。

| 参与方 | 能做什么 | 不能做什么 |
|---|---|---|
| 协调服务器 | 分发设备公钥、官方中转列表、房间成员关系 | 看到或转发用户数据；给已知设备换上别的公钥（客户端会校验） |
| 中转服务器（官方或房间中转） | 转发、丢弃、延迟数据包；看到设备 ID、地址、流量大小与时序 | 解密或篡改数据；冒充房间成员发送游戏发现；把数据注入本机 |
| 同一网络中的其他设备 | 在防火墙允许的范围内访问本机的服务 | 绕过防火墙；借本机访问本机所连的其他网络；冒充其他设备 |
| 本机的其他用户 | 查看核心状态（只读） | 修改网络状态（需要管理员角色） |

---

## 数据加密

- 设备之间的**所有**数据都经过 WireGuard 加密，直连和中转都一样，不存在明文模式
- 游戏发现数据同样在加密隧道内逐个发送给房间成员
- 伪造的 WireGuard 消息无法通过校验，不会改变任何会话状态

详见：[《连接机制》](/connect/basics/connections)

---

## 身份与公钥

- 设备 ID 由设备公钥推导而来；设备登记时必须证明自己持有私钥（密钥证明），首次登记的公钥会被协调服务器固定
- 客户端收到其他设备的公钥时会重新校验公钥与设备 ID 是否对应；未认证设备的用户 ID 也必须由其公钥推导
- 因此，即使协调服务器出错，也无法让一台设备冒充另一台已知设备，访客也无法冒用认证用户的用户 ID 去匹配用户级防火墙规则

详见：[《接入认证》](/connect/basics/authentication)、[《标识符》](/connect/basics/identifiers)

## 防范恶意设备

其他设备（包括房间中的陌生成员）发来的数据要经过以下检查：

| 检查 | 作用 |
|---|---|
| 来源地址必须是对端自己的虚拟 IP | 防火墙按来源设备的判断有密钥作保证 |
| 目的地址必须是本机的虚拟 IP | 对端无法借本机访问局域网或其他设备，即使本机开启了 IP 转发 |
| 对端的虚拟地址必须在 MSST-Net 地址范围内，且不与本机或其他设备重复 | 对端无法冒充互联网主机或接管其他设备的流量 |
| 防火墙规则（默认拒绝） | 只有规则或授权允许的端口才能访问 |
| ICMP 限制 | 只接受 ping 及其应答，以及针对本机发给该设备的数据包的差错报文；重定向、邻居发现等一律丢弃 |
| 游戏发现限制 | 只接受同一房间成员发来的 UDP 广播（MSST-Net 广播地址的任意端口）和两个发现组播组；按发送者限速，并以发送者自己的地址重建数据包 |
| 权限撤销 | 删除或禁用规则、退出房间时，已建立的连接会被切断（规则自然过期除外） |

对端通过协调服务器公布的信息也不会被直接采信：

- 直连候选地址中的环回、组播、广播、链路本地地址会被忽略，每台设备最多 16 个
- 对端公布的中转只有在官方中转列表中才会被使用
- 本机只回应已知设备的直连探测

## 防范恶意中转服务器

中转服务器能看到流量的元数据，也能丢弃或延迟数据包（这会影响可用性），但不能：

- 解密或篡改数据，或冒充任何设备发送数据
- 冒充房间成员发送游戏发现（3.1.5 及以前的游戏发现经中转分发，中转可以冒充房间成员；3.1.6 起已改为端到端发送）
- 冒用其他设备的 ID 登记地址（官方中转默认要求认证登记）

房间中转由建房人指定，可能是任何人自建的服务器，因此额外要求：

- 房间中转必须是**公网单播地址**，不能是环回、私有、CGNAT、链路本地等地址——否则建房人可以让所有成员向他们自己的局域网发送流量
- 房间中转不可用时，成员自动改用各自的偏好中转

详见：[《房间中转》](/connect/spaces/room_relay)、[《自托管中转服务器》](/connect/selfhost/relay)

## 本机安全

- 核心以特权运行，控制器以普通用户运行；能打开 IPC 套接字并不等于能操作核心：只有管理员角色（`msst-net` / `MSST-Net Administrators` 用户组成员等）可以修改状态，其他已登录用户只能查看
- 认证凭据不会发送给控制器，也不会写入日志
- 设备私钥 `private.key` 只有所有者可读
- Linux 上核心会关闭虚拟网卡的广播转发，避免房间成员的广播被内核转发回虚拟网卡

详见：[《系统架构》](/connect/basics/architecture)

## 运营建议

运营协调服务器或中转服务器时：

| 组件 | 建议设置 | 说明 |
|---|---|---|
| 协调服务器 | `device_key_proof: required` | 登记设备必须证明持有私钥（新部署的默认值） |
| 协调服务器 | `persistence.driver: sqlite` | 公钥固定在重启后仍然有效（新部署的默认值，数据库文件只有所有者可读） |
| 中转服务器 | `relay.register_auth: required` | 拒绝未认证的登记（新部署的默认值，需要配置协调服务器地址） |

协调服务器与中转服务器第一次启动时会把当时的默认值写入 `config.yaml`，已有部署需要手动修改上述设置。

## 已知局限

- 中转服务器能看到流量的元数据（设备 ID、地址、大小、时序），也能让经过它的通信中断
- 协调服务器是信任根：它被攻破时，可以影响官方中转列表、房间成员关系，以及**尚未登记过的**设备 ID 的公钥
- 设备 ID 只有 32 位：为一个**从未登记过**的设备 ID 暴力寻找匹配的密钥约需 2^32 次尝试；已登记的设备 ID 受公钥固定保护
- 与 3.1.5 及以前版本的设备之间没有游戏发现（不会降级到不安全的旧协议）
