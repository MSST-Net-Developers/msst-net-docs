## 总览

MSST-Net 由以下几部分组成：

| 组件 | 运行位置 | 职责 |
|---|---|---|
| 客户端核心（Core） | 每台接入设备 | 虚拟网卡、加密、选路、防火墙、DNS、游戏发现 |
| 客户端控制器（Controller） | 每台接入设备（或通过浏览器） | 图形界面，向核心发送操作请求、展示核心状态 |
| 协调服务器（Coordinator） | MSST-Net 服务端 | 设备登记、地址分配、房间、ezPlay 主机名、接入认证 |
| 中转服务器（Relay） | MSST-Net 服务端，或自行部署 | 在无法直连时转发加密后的数据 |
| MSST 联合认证平台 | MSST 服务端 | 账号与身份认证 |

```text
  控制器 ──IPC──► 客户端核心 ──WebSocket / HTTPS──► 协调服务器 ──► MSST 联合认证平台
                     │
                     ├──UDP（直连）────────────────► 对端设备
                     └──UDP（中转）──► 中转服务器 ──► 对端设备
```

## 客户端核心

客户端核心是运行在每台设备上的**特权进程**，是本机网络状态的唯一权威来源。

它负责：

- 创建虚拟网卡（默认名称 `msst0`）并配置虚拟地址
- 用 WireGuard 加密与对端之间的全部数据
- 选择连接路径（直连或中转）
- 执行防火墙规则与交互式授权
- 在本机解析 `*.msst.net` 域名
- 在房间成员之间端到端转发游戏的局域网发现广播

即使控制器关闭，核心也会持续运行，网络连接不受影响。

核心使用的本机端口：

| 端口 | 用途 |
|---|---|
| UDP 21031 | 数据通道（直连与中转），游戏发现也走这个通道 |
| UDP 127.0.0.1:21053（Windows 为 127.0.0.1:53） | 本机 DNS 解析 |
| TCP 127.0.0.1:9100 | Prometheus 指标（只监听本机） |

> 3.1.5 及以前还使用 UDP 21032 收发游戏发现数据；3.1.6 起游戏发现改走加密隧道，不再使用该端口。

## 客户端控制器

控制器是**非特权**的图形界面程序，通过本机 IPC 与核心通信：

- Linux：Unix 域套接字 `/run/msst-net/ipc.sock`（macOS 为 `/var/run/msst-net/ipc.sock`）
- Windows：命名管道 `\\.\pipe\msst-net-ipc`
- Android：核心内嵌在应用中，通过应用私有的套接字通信

控制器只负责展示核心报告的状态、把用户的操作转交给核心，**不直接修改任何网络状态**。

### 访问权限

能打开套接字并不等于能操作核心。核心会根据连接方的系统身份（由操作系统提供，无法伪造）决定权限：

| 角色 | 可以做什么 | 谁属于这个角色 |
|---|---|---|
| 管理员 | 查询状态，以及全部操作（建房、修改规则、修改设置等） | root / LocalSystem、核心自身的运行用户、通过 `sudo` 启动核心的用户、本地用户组 **`msst-net`**（Linux / macOS）或 **`MSST-Net Administrators`**（Windows）的成员、以管理员身份运行的程序（Windows） |
| 只读 | 查询状态、接收事件，不能做任何修改 | 其他已登录本机的用户 |

只读角色在控制器中会显示为只读界面。安装程序会创建上述用户组并把安装用户加入其中；加入用户组后重新连接即可生效，无需重启核心。

控制器重新打开或重新连接时，会先向核心读取完整状态，再接收后续的变更通知，因此不会因为关闭过控制器而显示过时的信息。

详见：[《控制器说明》](/connect/install/controller)

## 协调服务器

协调服务器是 MSST-Net 的控制面，负责：

- 设备上线、登记与在线状态
- 由设备 ID 推导虚拟 IP 地址，并处理地址冲突
- 分配 ezPlay 主机名，提供 `*.msst.net` 解析数据
- 房间的创建、加入、成员同步与房间密码校验
- 对接 MSST 联合认证平台（OIDC 设备授权流程），以及签发访客凭据
- 登记中转服务器并向客户端公布可用的官方中转（以及中转的公钥）
- 管理自定义 `.msst.net` 命名空间
- 校验登记设备确实持有其密钥（**密钥证明**），并固定每个设备 ID 的公钥

设备公钥、用户与房间等数据默认保存在协调服务器本地的 SQLite 数据库中，重启后仍然有效。

客户端核心与协调服务器之间通过 WebSocket 保持长连接，并使用 HTTPS 接口完成登记、建房等操作。

协调服务器**不转发任何用户数据**。协调服务器暂时不可用时，已经建立的连接仍可继续通信，但无法加入新房间或发现新上线的设备。

默认协调服务器地址：

```text
https://coord.msst-net.msst2031.cn
```

## 中转服务器

中转服务器只做一件事：在设备之间**原样转发**已经加密的数据包。

- 中转服务器看不到通信内容（数据经 WireGuard 端到端加密），游戏发现数据同样在加密隧道内传输
- 中转服务器能看到设备 ID、公网地址、流量大小与时序
- 设备向中转登记地址时需要用设备私钥签名（**认证登记**），其他人无法冒用设备 ID 截走流量

中转服务器分为两类：

| 类型 | 说明 |
|---|---|
| 官方中转 | 由 MSST-Net 运营，出现在协调服务器公布的中转列表中，所有设备都可以自动选用 |
| 自托管中转 | 由任何人自行部署，不公开列出，只能由房主在建房时通过连接串指定为**房间中转** |

详见：

- [《连接机制》](/connect/basics/connections)
- [《房间中转》](/connect/spaces/room_relay)
- [《自托管中转服务器》](/connect/selfhost/relay)

## 信任边界

| 组件 | 可以信任它做什么 | 不需要信任它做什么 |
|---|---|---|
| 协调服务器 | 分发设备公钥、官方中转列表、房间成员关系 | 看到或转发用户数据 |
| 官方中转 / 房间中转 | 转发数据包 | 保密、完整性、发送者身份（都由端到端加密保证） |
| 其他设备 | — | 任何事：它发来的数据都要经过加密校验、地址校验与防火墙 |

客户端会自行校验协调服务器下发的数据：对端的公钥必须与其设备 ID 对应，对端的虚拟地址必须在 MSST-Net 网段内，对端公布的中转必须是官方中转。

详见：[《安全模型》](/connect/basics/security)
