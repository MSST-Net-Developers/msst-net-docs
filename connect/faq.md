## 安装与启动

### 安装客户端后，控制器无法检测到核心？

请检查以下几点：

1. 确认客户端核心正在运行
2. 若配置了系统服务，检查服务状态：
   ```bash
   sudo systemctl status msst-net
   ```
3. Linux / macOS 上，若核心以 root 运行，请确认当前账号已加入 `msst-net` 用户组（加入后需重新登录系统）；否则控制器只能以只读方式连接，或被拒绝连接
4. 若核心使用了非默认的 IPC 路径，请为控制器设置相同的 `MSST_IPC_PATH` 环境变量
5. 查看核心日志获取错误信息

详见：[《控制器说明》](/connect/install/controller#连接客户端核心)

---

### 控制器显示"只读"，无法修改任何设置？

客户端核心只给当前系统用户授予了**只读**权限。请将该用户加入 `msst-net` 用户组：

```bash
sudo groupadd -f msst-net
sudo usermod -aG msst-net $USER
```

重新登录系统后即可获得管理权限，无需重启核心。

---

### 客户端启动后，未生成设备 ID？

设备 ID 在首次启动时自动生成，保存在数据目录的 `identity.json` 中（Linux 默认为 `~/.local/share/msst-net/`，从 3.0.x 升级的设备沿用 `~/MSST-Net/`）。

若该文件不存在，核心会在启动时自动创建。若仍未生成，请检查核心是否有写入该目录的权限。

详见：[《客户端配置》](/connect/install/configuration#数据目录)

---

### 3.1 客户端能和 3.0.x 客户端通信吗？

不能。3.1 起所有设备间数据都经 WireGuard 加密，与 3.0.x 不兼容。请确保需要互相通信的设备都升级到 3.1。

升级时，设备 ID、虚拟 IP 和防火墙规则会自动保留。

## 连接问题

### 为什么无法连接到对端设备？

请按以下顺序排查：

1. **确认两台设备均已上线**：在控制器中查看对端设备的在线状态
2. **确认身份限制**：若任一方未完成认证，双方必须在同一房间内才能通信
3. **确认加密会话**：在 **设置 → 诊断与调试 → 路径视图** 中查看对端的加密状态是否为"已加密"
4. **检查防火墙规则**：请对端在 **防御 → 访问记录** 中查看你的访问是否被拒绝

详见：[《诊断工具》](/connect/troubleshoot/diagnostics)

---

### 为什么直连没有建立，一直走中转？

直连需要满足以下条件：

- 对端的直连候选地址已获取
- 对某个候选地址连续收到 5 次探测回包
- 直连路径的往返延迟不高于中转路径

若网络环境（如严格 NAT、对称 NAT）无法穿透，直连可能永远无法建立，流量会始终通过中转转发。这是正常现象，不影响正常使用。

连续探测失败后，系统会逐步拉长探测间隔（最长 10 分钟），路径视图中会显示失败轮数与下一次探测时间。

另外，若开启了 **禁用 P2P 直连**，也不会建立直连。

---

### 连接延迟很高怎么办？

1. 检查当前路径模式：若为直连（Direct），延迟高可能是网络本身问题
2. 若为中转模式，可在 **设置 → 诊断与调试 → 高级选项** 中指定距离更近的中转（**中转服务器偏好**）
3. 房间成员集中在某一地区时，房主可以在建房时指定一台合适的 **房间中转**
4. 检查本机网络质量，排查本机 ISP 或 Wi-Fi 问题

---

## 防火墙与授权

### 为什么连接对端时弹出了授权请求？

当有设备尝试访问本机某端口，且没有匹配的防火墙规则时，系统会触发**交互式授权**请求。

这是正常的安全机制。你可以选择：

- **允许**：临时放行，10 分钟后失效
- **始终允许**：永久放行，自动创建规则
- **拒绝** / **始终拒绝**：临时或永久拒绝

详见：[《交互式授权》](/connect/acl/interactive_auth)

---

### 对方已经同意了授权，为什么我第一次还是连接失败？

等待授权期间，TCP 连接会立即被重置，以免程序长时间卡住。对方同意后，**重新连接一次**即可。

UDP 数据则会在等待期间被缓冲，同意后自动补发。

---

### 为什么没有弹出授权请求，对端直接连接失败了？

不在房间内时，交互式授权只对**特定来源**的设备触发：本账号的其他设备、最近 7 天内联系过的设备、以及在设备级规则中引用过的设备。其他陌生设备的连接请求会被**静默丢弃**。

另外，同时待处理的请求过多时也不会再弹出提示；使用 WebUI 版控制器时则不会显示授权请求。

若需要允许某陌生设备访问，请先手动创建防火墙规则，或与对方在同一房间中。

---

### ping 对端没有响应？

ICMP ping（`ping` 命令）默认被拒绝。

若需要允许 ping，请对端在控制器的 **防御** 页面中打开 **Ping (ICMP)** 开关。

---

### 修改权限组后，规则没有变化？

这是预期行为。权限组在创建规则时展开为成员列表，之后修改权限组不会改变已创建的规则。请用修改后的权限组重新创建规则。

详见：[《权限组》](/connect/acl/groups)

---

## 标识符与主机名

### 如何修改设备的显示名称？

在控制器的**设置**页面，可以修改：

- 设备名（显示名称，会展示给房间内的其他成员）
- 设备助记符（用于规则引用和 ezPlay 主机名）

修改助记符后，ezPlay 主机名会随之更新。

---

### 已认证用户可以修改用户助记符吗？

若已完成接入认证，用户助记符与用户显示名称取自认证账号，由协调服务器管理，本地修改**不会生效**。

---

### ezPlay 主机名解析失败？

请检查以下几点：

1. 确认使用的是完整后缀 `.ezplay.msst.net`（如 `archlinux.abjust.ezplay.msst.net`）
2. 确认客户端核心正在运行（`*.msst.net` 由核心在本机解析）
3. 确认目标设备在线，且与本机处于同一网络（大内网或房间）
4. Linux 上若系统未使用 systemd-resolved，可尝试将 **DNS 配置模式** 改为"仅使用 DNS 拦截"

---

## 房间模式

### 创建或加入房间时提示"已在房间中"？

一台设备同一时间只能在一个房间内。请先退出当前房间，再创建或加入新的房间。

---

### 免认证用户创建的房间有人数限制吗？

没有。自 3.1 起，所有房间都没有成员数量限制。

---

### 游戏的局域网联机选项搜不到房间？

1. 确认两台设备已在同一 MSST-Net 房间内
2. 局域网发现功能仅在**桌面端（Windows / Linux / macOS）**支持，Android 不支持
3. 确认游戏使用的是发现支持的协议（Minecraft Java LAN 广播、mDNS 等）
4. 在 **设置 → 诊断与调试 → 游戏发现** 中检查是否有发现包被丢弃
5. 部分游戏可能需要手动输入 IP 或 ezPlay 主机名而非自动发现

---

### 离开房间后，虚拟 IP 还有效吗？

有效。设备的虚拟 IP 是由设备 ID 确定性推导的固定地址，与是否在房间内无关，始终有效。

离开房间只是停止局域网发现，并不影响虚拟 IP 本身。但免认证用户离开房间后，将无法再与任何设备通信。

---

## 数据与隐私

### 设备数据存储在哪里？

客户端数据默认存储在：

- **Linux**：`~/.local/share/msst-net/`
- **macOS**：`~/Library/Application Support/msst-net/`
- **Windows**：`%APPDATA%\msst-net\`
- **从 3.0.x 升级的设备**：沿用 `~/MSST-Net/`（容器部署为 `/var/lib/msst/`）

该目录包含设备身份信息、密钥、防火墙规则、权限组及网络设置等。

---

### 私钥文件可以迁移吗？

可以。将数据目录中的 `private.key` 和 `identity.json` 复制到新设备的数据目录，重启核心后即可恢复设备身份（设备 ID 与虚拟 IP 不变）。如需保留防火墙规则，也一并复制 `firewall_rules.json` 和 `permission_groups.json`。

> **注意**：私钥文件请妥善保管，切勿泄露。泄露私钥将导致他人冒充你的设备。同一份私钥不要同时在两台设备上使用。

---

### 中转服务器能看到我的通信内容吗？

不能。所有设备间数据都经 WireGuard 端到端加密，中转服务器（包括自托管中转）只能看到设备 ID、公网地址和流量时序，以及游戏发现的内容。

详见：[《连接机制》](/connect/basics/connections#数据加密)
