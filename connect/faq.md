## 安装与启动

### 安装客户端后，控制器无法检测到核心？

请检查以下几点：

1. 确认客户端核心正在运行
2. 若配置了系统服务，检查服务状态：
   ```bash
   sudo systemctl status msst-net
   ```
3. 若核心以 root / 系统服务运行，请确认当前账号已加入管理员组（Linux / macOS：`msst-net`；Windows：`MSST-Net Administrators`）；否则控制器只能以只读方式连接，或被拒绝连接
4. 若核心使用了非默认的 IPC 路径，请为控制器设置相同的 `MSST_IPC_PATH` 环境变量
5. 查看核心日志获取错误信息

详见：[《控制器说明》](/connect/install/controller#连接客户端核心)

---

### 控制器显示"只读"，无法修改任何设置？

客户端核心只给当前系统用户授予了**只读**权限。请将该用户加入管理员组。

Linux / macOS：

```bash
sudo groupadd -f msst-net
sudo usermod -aG msst-net $USER
```

Windows（以管理员身份打开命令提示符，`<用户名>` 换成日常使用的账号）：

```bat
net localgroup "MSST-Net Administrators" <用户名> /add
```

加入后**重新打开控制器**即可获得管理权限，无需重新登录系统，也无需重启核心。

::: tip Windows：3.1.9 及以前
3.1.9 及以前的 Windows 核心只认登录时的组成员关系，加组后需要注销并重新登录 Windows 才生效。升级到 3.1.10 即可直接生效。

另外，3.1.4 及以前的安装器在"普通用户输入管理员密码"提权时，会把输入密码的管理员账号（而不是你自己）加入管理员组。3.1.5 起改为加入当前桌面登录的用户。
:::

---

### 客户端启动后，未生成设备 ID？

设备 ID 在首次启动时自动生成，保存在数据目录的 `identity.json` 中（Linux 默认为 `~/.local/share/msst-net/`，从 3.0.x 升级的设备沿用 `~/MSST-Net/`）。

若该文件不存在，核心会在启动时自动创建。若仍未生成，请检查核心是否有写入该目录的权限。

详见：[《客户端配置》](/connect/install/configuration#数据目录)

---

### 3.1 客户端能和 3.0.x 客户端通信吗？

不能。3.1 起所有设备间数据都经 WireGuard 加密，与 3.0.x 不兼容。请确保需要互相通信的设备都升级到 3.1。

升级时，设备 ID、虚拟 IP 和防火墙规则会自动保留。

---

### 3.1.6 能和 3.1.5 及以前的 3.1 客户端一起使用吗？

可以，只有**游戏发现**不互通：3.1.6 的游戏发现改为在加密隧道内端到端发送，不会为了兼容而退回旧方式。房间成员卡片上会标出版本过旧的成员。需要互相发现游戏的设备请都升级到 3.1.6。

详见：[《房间模式》](/connect/spaces/room_space#游戏发现)

---

### 房间指定了中转服务器，却总是提示“房间中转服务器不可用”？

如果房间中转与你自己的中转是同一台（例如都是官方的 `us1`），3.1.8 及以前的客户端会在加入房间约 10 秒后误判它不可用，房间流量照常经各自的偏好中转，连接不受影响。升级到 3.1.9 即可修复。如果升级后仍然提示不可用，再检查中转本身是否在线。

详见：[《房间中转》](/connect/spaces/room_relay#可用性与自动回退)

---

### 3.1.10 能和旧版本一起使用吗？

可以，网络互通不受影响。3.1.10 的控制器连接旧版核心时，规则编辑、权限组关联、名称识别和核心版本的更新检查不可用（只能修改备注和启用状态），升级核心后即可使用。

3.1.10 的核心和控制器可以继续用 3.1.4 的安装器安装；在系统防火墙中放行 UDP 端口、以及 Windows 上把桌面登录用户加入管理员组，需要 3.1.5 的安装器（核心启动时也会自行补上防火墙规则）。

---

### 控制器提示"发现新版本"？

3.1.10 起，桌面端控制器和 WebUI 每天检查一次 GitHub / Gitee 上的最新正式版，发现核心或控制器有新版本时在顶部提示。控制器不会自动更新：请按提示下载最新的客户端安装器，以管理员身份运行并选择 **升级**。Android 应用只检查自身版本，请下载新的 APK 覆盖安装。

关闭提示后，本次运行期间不再提醒，有更新的版本时会再次提醒。不需要检查更新时，可为控制器设置环境变量 `MSST_UPDATE_CHECK=0`。命令行控制器可随时运行 `msst-net-cli check-update` 检查。

---

### 3.1.8 能和旧版本一起使用吗？

可以，3.1.8 与 3.1.7 及以前的 3.1 客户端完全互通。切换网络后的快速恢复主要在切换网络的那台设备上生效；控制器显示路径切换原因需要核心也是 3.1.8。

用客户端安装器安装 3.1.8 的控制器时，需要 3.1.4 或更新的安装器。

---

## 连接问题

### 为什么无法连接到对端设备？

请按以下顺序排查：

1. **确认两台设备均已上线**：在控制器中查看对端设备的在线状态
2. **确认身份限制**：若任一方未完成认证，双方必须在同一房间内才能通信
3. **确认加密会话**：在 **设置 → 诊断与调试 → 路径视图** 中查看对端的加密状态是否为"已加密"
4. **检查防火墙规则**：请对端在 **防御 → 访问记录** 中查看你的访问是否被拒绝

详见：[《诊断工具》](/connect/troubleshoot/diagnostics)

---

### 为什么直连没有建立，一直走中转？

直连需要满足以下条件：

- 对端的直连候选地址已获取
- 对某个候选地址连续收到 5 次探测回包
- 直连路径的往返延迟不高于中转路径

若网络环境（如严格 NAT、对称 NAT）无法穿透，直连可能永远无法建立，流量会始终通过中转转发。这是正常现象，不影响正常使用。

**系统防火墙**也会影响直连：它会丢弃对端主动发来的 UDP 数据包，局域网直连、IPv6 直连尤其容易失败。3.1.10 起，安装器会在系统防火墙中放行核心的 UDP 端口（默认 21031），核心每次启动时也会检查并补上这条规则，详见 [《安装客户端》](/connect/install/client#系统防火墙)。使用自定义 nftables / iptables 规则的 Linux 主机，需要自行放行入站 UDP 21031。

连续探测失败后，系统会逐步拉长探测间隔（最长 10 分钟），路径视图中会显示失败轮数与下一次探测时间。

另外：

- 若任一方开启了 **禁用 P2P 直连**，不会建立直连（开启时已有的直连也会立即降回中转）
- 直连探测只会得到**已知设备**的应答：两台设备刚开始通信、对方还没有获取到本机信息时，第一轮探测可能失败，之后会自动重试
- 路径视图中的切换原因为"直连能 ping 通但数据不通"时，说明这条直连只放行小的探测包、却丢弃了正常数据（常见于 MTU 问题）。系统会暂时不再使用这个地址（1 分钟起，最长 10 分钟）；若在高级选项中调大过 MTU，可以改回自动（1280）

---

### 切换网络后，多久能恢复连接？

以 3.1.8 为例，在 Wi-Fi 与手机热点之间切换时：

- 切换网络的设备约 2–4 秒内发现地址变化，立即重连协调服务器、向中转重新登记并上报新端点
- 已失效的直连约 5 秒内降回中转，经中转的通信随即恢复
- 对端收到新端点后重新探测，条件满足时再升级为直连
- 切换不超过约 1 分钟时，设备不会离开房间

3.1.8 从支持 IPv6 的网络（例如手机热点）切换到不支持 IPv6 的网络时，中转路径可能要等重新选择中转后才恢复，加密会话偶尔会中断数分钟；3.1.9 已修复。

若切换网络的设备仍是 3.1.7 及以前的版本，恢复可能需要几分钟，期间它会被移出房间、游戏发现中断。请升级经常切换网络的设备。

详见：[《连接机制》](/connect/basics/connections#网络切换)

---

### 连接延迟很高怎么办？

1. 检查当前路径模式：若为直连（Direct），延迟高可能是网络本身问题
2. 若为中转模式，可在 **设置 → 诊断与调试 → 高级选项** 中指定距离更近的官方中转（**中转服务器偏好**）
3. 房间成员集中在某一地区时，房主可以在建房时指定一台合适的 **房间中转**
4. 检查本机网络质量，排查本机 ISP 或 Wi-Fi 问题

---

## 防火墙与授权

### 为什么连接对端时弹出了授权请求？

当有设备尝试访问本机某端口，且没有匹配的防火墙规则时，系统会触发**交互式授权**请求。

这是正常的安全机制。你可以选择：

- **允许**：临时放行，10 分钟后失效
- **始终允许**：永久放行，自动创建规则
- **拒绝** / **始终拒绝**：临时或永久拒绝

详见：[《交互式授权》](/connect/acl/interactive_auth)

---

### 对方已经同意了授权，为什么我第一次还是连接失败？

等待授权期间，TCP 连接会立即被重置，以免程序长时间卡住。对方同意后，**重新连接一次**即可。

UDP 数据则会在等待期间被缓冲，同意后自动补发。

---

### 为什么没有弹出授权请求，对端直接连接失败了？

不在房间内时，交互式授权只对**特定来源**的设备触发：本账号的其他设备、最近 7 天内联系过的设备、以及在设备级规则中引用过的设备。其他陌生设备的连接请求会被**静默丢弃**。

另外，同时待处理的请求过多时也不会再弹出提示；使用 WebUI 版控制器时则不会显示授权请求。

若需要允许某陌生设备访问，请先手动创建防火墙规则，或与对方在同一房间中。

---

### ping 对端没有响应？

ICMP ping（`ping` 命令）默认被拒绝。

若需要允许 ping，请对端在控制器的 **防御** 页面中打开 **Ping (ICMP)** 开关。

---

### 删除规则后，对方已经建立的连接还会继续吗？

不会。删除、停用或清空规则后，由这些规则放行的连接会被**立即切断**；对方的下一个数据包会重新按规则判断。

但规则**自然到期**时不会切断已建立的连接，例如通过"允许"（10 分钟）授权后已经开始的游戏可以继续。

详见：[《防火墙规则》](/connect/acl/rules#连接跟踪)

---

### 修改权限组后，规则没有变化？

3.1.10 起，使用权限组创建的规则会随权限组的成员自动更新。没有变化的规则是 3.1.9 及以前创建的：当时规则只复制了权限组的成员，没有记录来自哪个权限组。编辑这条规则，把来源重新选为该权限组即可关联。

### 为什么不能编辑某条规则？

设有有效期的**临时规则**（例如交互式授权中选择"允许 / 拒绝"生成的规则）只能查看和删除，到期后自动删除。永久规则可以编辑全部内容；Android 上只能修改备注和启用状态。

详见：[《权限组》](/connect/acl/groups)

---

## 标识符与主机名

### 如何修改设备的显示名称？

在控制器的**设置**页面，可以修改：

- 设备名（显示名称，会展示给房间内的其他成员）
- 设备助记符（用于规则引用和 ezPlay 主机名）

修改助记符后，ezPlay 主机名会随之更新。

---

### 已认证用户可以修改用户助记符吗？

若已完成接入认证，用户助记符与用户显示名称取自认证账号，由协调服务器管理，本地修改**不会生效**。

---

### ezPlay 主机名解析失败？

请检查以下几点：

1. 确认使用的是完整后缀 `.ezplay.net.msst2031.cn`（如 `archlinux.abjust.ezplay.net.msst2031.cn`）。3.1.6 及以前的 `.ezplay.msst.net` 已不再解析，本机需要是 3.1.7 或更新版本
2. 确认客户端核心正在运行（`*.net.msst2031.cn` 由核心在本机解析）
3. 确认目标设备在线，且与本机处于同一网络（大内网或房间）
4. Linux 上若系统未使用 systemd-resolved，可尝试将 **DNS 配置模式** 改为"仅使用 DNS 拦截"

---

## 房间模式

### 创建或加入房间时提示"已在房间中"？

一台设备同一时间只能在一个房间内。请先退出当前房间，再创建或加入新的房间。

---

### 免认证用户创建的房间有人数限制吗？

没有。自 3.1 起，所有房间都没有成员数量限制。

---

### 游戏的局域网联机选项搜不到房间？

1. 确认两台设备已在同一 MSST-Net 房间内
2. 游戏发现仅在**桌面端（Windows / Linux / macOS）**支持，Android 不支持
3. 确认双方都使用 3.1.6 或更新的客户端：成员卡片上显示"该成员版本过旧"时，双方之间没有游戏发现
4. 确认游戏使用的是支持的发现方式（Minecraft Java 版组播、mDNS、发往 MSST-Net 广播地址的 UDP 广播等）
5. 切换过网络（例如换到手机热点）后搜不到：请将双方升级到 3.1.8。3.1.7 及以前，Linux、macOS 在切换网络后会丢弃本机发出的广播，切换网络的设备还可能暂时被移出房间
6. 在 **设置 → 诊断与调试 → 游戏发现** 中检查发送、接收和丢弃的计数
7. 部分游戏可能需要手动输入 IP 或 ezPlay 主机名而非自动发现

---

### 控制器自己离开了房间？

房间在超过 2 分钟没有任何成员保活时会被协调服务器回收（例如所有成员的设备都休眠了）。设备恢复后，客户端得知房间已失效，会自动退出房间，控制器回到首页。

如需继续联机，请重新创建房间。

---

### 离开房间后，虚拟 IP 还有效吗？

有效。设备的虚拟 IP 是由设备 ID 确定性推导的固定地址，与是否在房间内无关，始终有效。

离开房间会停止游戏发现，并切断只因房间而放行的连接（房间级规则放行的连接，以及与访客设备之间的连接），但不影响虚拟 IP 本身。免认证用户离开房间后，将无法再与任何设备通信。

---

## 数据与隐私

### 设备数据存储在哪里？

客户端数据默认存储在：

- **Linux**：`~/.local/share/msst-net/`
- **macOS**：`~/Library/Application Support/msst-net/`
- **Windows**：`%APPDATA%\msst-net\`
- **从 3.0.x 升级的设备**：沿用 `~/MSST-Net/`（容器部署为 `/var/lib/msst/`）

该目录包含设备身份信息、密钥、防火墙规则、权限组及网络设置等。

---

### 私钥文件可以迁移吗？

可以。将数据目录中的 `private.key` 和 `identity.json` 复制到新设备的数据目录，重启核心后即可恢复设备身份（设备 ID 与虚拟 IP 不变）。如需保留防火墙规则，也一并复制 `firewall_rules.json` 和 `permission_groups.json`。

> **注意**：私钥文件请妥善保管，切勿泄露。泄露私钥将导致他人冒充你的设备。同一份私钥不要同时在两台设备上使用。

---

### 中转服务器能看到我的通信内容吗？

不能。所有设备间数据都经 WireGuard 端到端加密，3.1.6 起游戏发现也是如此。中转服务器（包括自托管中转）只能看到设备 ID、公网地址和流量时序（3.1.5 及以前的客户端还会让中转看到游戏发现的内容）。

详见：[《连接机制》](/connect/basics/connections#数据加密)、[《安全模型》](/connect/basics/security)

---

### 为什么不能把中转服务器偏好设成自己的中转？

**中转服务器偏好**只支持官方中转。自建的中转只能由房主在建房时指定为**房间中转**。

对端公布的中转同样只有官方中转会被使用：否则任何设备都能让别人向任意服务器发送数据，或借此得知别人的公网地址。

详见：[《连接机制》](/connect/basics/connections#手动指定)、[《房间中转》](/connect/spaces/room_relay)
